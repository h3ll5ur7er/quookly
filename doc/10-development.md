# Development and contribution

**Status: Built — everything in this document works today.**

## Setup

See [Installation](09-installation.md#running-from-source--built). In short:

```bash
just install && just openapi
```

Then, in two terminals:

```bash
just backend run
```

```bash
just frontend serve
```

The backend serves the API on `:8000`; the Angular dev server runs on `:4200` with live reload.
CORS is open in development.

## Ground rules

These are not style preferences. Breaking them breaks the build or the architecture.

### Use the tool managers

**Python is managed by uv.** `pip install`, `uv pip install`, and `python -m pip install` are
prohibited, as is hand-editing `[project.dependencies]`.

```bash
uv add httpx
```

```bash
uv add --dev pytest-cov
```

Run things with `uv run <thing>`. Lockfiles are committed; let uv update them.

**Node is managed by nvm.** Never call `npm` or `ng` from a bare shell — the frontend pins Node
v24.15.0 and the justfile sources nvm for every command. Go through `just frontend <cmd>`. For
anything ad-hoc:

```bash
just frontend _nvm "npm install some-package"
```

**just is the entry point.** If a recipe exists, use it. `just --list` in any directory shows what
is available.

### Never edit generated code

Three directories are generated and will be overwritten without warning:

| Path | Generated by |
| --- | --- |
| `frontend/src/api/` | `just frontend generate-openapi-client` |
| `cli/src/quookly_cli/api_client/` | `just cli generate-openapi-client` |
| `backend/src/quookly/app/` | `just frontend build` |

`openapi.json` is generated too — it is exported from the backend, never hand-edited.

### Regenerate after every API change

```bash
just openapi
```

The backend is the single source of truth for the API contract. Both clients are generated from it.
Hand-written HTTP calls or DTOs in the frontend or CLI are a defect, not a shortcut.

**Route function names are public API.** `def create_recipe()` becomes `createRecipe()` in Angular
and `create_recipe.asyncio(...)` in the CLI, and must be unique within its tag — the operationId
generator raises on collision. Name handlers deliberately.

### Respect the layers

Before adding code, read [Architecture](04-architecture.md#call-rules) and place it by volatility,
not by feature. The short version:

- Managers sequence; they do not compute. Business rules belong in engines.
- Rule engines are pure — no I/O, inputs as arguments. This is what makes the safety-critical
  suitability logic testable.
- Resource access speaks domain verbs, not table operations.
- No Manager calls another Manager. Use the event bus.

Once [ADR-008](07-decisions.md#adr-008-enforce-the-call-rules-with-import-linter) lands, violations
fail `just backend check` rather than review.

## The development loop

Quality, architecture, and documentation are not a phase at the end. They are part of every unit of
work ([ADR-017](07-decisions.md#adr-017-test-driven-development-with-per-unit-quality-gates)).

### Test-driven, without exception

1. **Read the specification.** The use case in [Requirements](02-requirements.md), the flow in
   [Use case flows](05-use-case-flows.md), the volatility it belongs to.
2. **Write the failing test.** It must fail for the right reason — run it and read the failure. A
   test that passes before the implementation exists is testing nothing.
3. **Implement until green.** The simplest thing that passes.
4. **Refactor** with the test green.

This architecture makes step 2 unusually cheap, which is a deliberate benefit rather than a
coincidence. Rule engines are pure functions, so their tests are a table of inputs and expected
outputs — no database, no fixtures, no mocks, no async. `SuitabilityEngine` in particular can be
specified entirely as cases, which is exactly the property a safety-critical component needs.

If a specification cannot be turned into a test, stop. That usually means the requirement is not yet
understood, and writing the code first will not clarify it.

### The quality gate

At the end of **every unit of implementation** — not every pull request:

```bash
just check
```

Then, before moving on:

| Gate | Question |
| --- | --- |
| **Lint and typecheck** | Included in `just check`. Green, no suppressions added. |
| **All tests** | The whole suite, not just the ones you touched. |
| **Review and refactor** | Read what you wrote as if reviewing it. Duplication, unclear names, functions doing two things. |
| **Architecture alignment** | Right layer? Any Manager→Manager call? Did a rule engine acquire I/O? Does it match [Architecture](04-architecture.md)? |
| **Documentation** | Does this change a decision, a volatility, a flow, or a requirement? Update the document in the same commit. |

Running the gate per unit is what keeps its cost flat. A layer violation caught immediately is a
one-line fix; the same violation found a week later, after three things were built on top of it, is
a refactor.

**Documentation drift is a defect.** A pull request that changes behaviour and leaves the documents
describing the old behaviour is incomplete, in the same way that one leaving a failing test is.

### When the architecture resists

If a change is awkward to place, that is information. Do not force it into the nearest service. It
usually means one of:

- The volatility is new — add it to [Volatility analysis](03-volatility-analysis.md).
- The volatility is misplaced — an existing service is covering two things that change for different
  reasons.
- The requirement is not understood yet.

Say which in the pull request. Ignoring the resistance is how a decomposition rots.

## Migrations

The schema of record is the migration history, not the models. A running instance is built
by `alembic upgrade`, so a model change without a migration produces a schema that exists only
in tests.

```bash
just backend makemigration "what changed"
```

```bash
just backend migrate
```

The migration is autogenerated from SQLModel's metadata and **must be reviewed before
committing** — autogenerate is a good first draft, not an answer. It cannot see renames (it emits a
drop plus an add, which discards data) and it does not know your intent about defaults for existing
rows.

`tests/access/test_migrations.py` fails if the models and the migrations disagree, so drift is
caught by the gate rather than in production. SQLite cannot `ALTER` most things in place, so the
environment renders migrations in batch mode, which rewrites the table instead.

## Testing

| Project | Runner | Location |
| --- | --- | --- |
| Backend | pytest, `asyncio_mode = "auto"` | `backend/tests/` |
| CLI | pytest, `asyncio_mode = "auto"` | `cli/tests/` |
| Frontend | Vitest via `@angular/build:unit-test` | alongside sources as `*.spec.ts` |
| End to end | Playwright + axe, in Chromium | `frontend/e2e/` |

Frontend specs use `provideHttpClientTesting` and assert against `HttpTestingController` rather than
a mocked service, so the generated client is exercised rather than bypassed. Where a component
navigates, stub `Router.navigateByUrl` in setup — a real router with no routes registered rejects,
and the rejection surfaces as an unhandled error in a later test rather than the one that caused it.

Async tests need no `@pytest.mark.asyncio` — auto mode is configured.

Tests are written **before** the implementation
([ADR-017](07-decisions.md#adr-017-test-driven-development-with-per-unit-quality-gates)). See
[The development loop](#the-development-loop).

Test at the layer you are working in:

- **Rule engines** — pure functions, so test them exhaustively with no fixtures or mocks.
  `SuitabilityEngine` in particular is safety-critical
  ([ADR-006](07-decisions.md#adr-006-allergen-determination-is-structural)); it should have the
  densest tests in the repository, including the *unknown ingredient* case.
- **Managers** — test sequencing with test doubles for the engines and access services they use.
- **Resource access** — test against the real datastore.
- **Routes** — test wiring and contract shape, not business rules.

### End-to-end

```bash
just e2e
```

Builds the application, serves it from the backend on a **fresh database**, and drives it in a real
browser on a phone viewport — the artefact a self-hoster runs, not the dev server.

Three things it covers that nothing else can:

- **Accessibility.** `@axe-core/playwright` runs on every screen in every theme. NFR-7 was
  previously a claim; this is the check.
- **The whole journey**, including the parts that only happen once: an unclaimed instance, the
  bootstrap closing behind itself, the guard remembering where a stranger was going.
- **What it looks like.** `e2e/03-looks.spec.ts` writes screenshots to `e2e/screenshots/` for a
  human to look at. It asserts nothing about appearance — a suite that passes is not the same as a
  screen that is good, and the only way to know the difference is to look.

The suite runs with **one worker, in file order**, because the tests share one backend and one
database and claiming an instance is a one-way door. Tests that need a claimed instance create one
through the API in `beforeAll` rather than depending on an earlier file having run.

It is a separate gate from `just check`: it builds and drives a browser, so it is slower than
something you run after every unit. Run it before opening a pull request that touches the frontend.

Playwright needs its browser once:

```bash
just frontend _nvm "npx playwright install chromium"
```

## Type checking

Both Python projects run **strict mypy** and are currently clean. Keep them that way — annotate
every function, including tests.

The frontend typecheck runs `ngc --noEmit` over both tsconfigs, which checks **Angular templates**
under `strictTemplates`. Plain `tsc` does not catch template errors, so use `just frontend
typecheck` rather than invoking `tsc` directly.

## Frontend conventions

`frontend/AGENTS.md` is the authoritative Angular style guide — signals, standalone components,
`inject()`, native control flow, OnPush, WCAG AA. Read it before writing components.

It is wired in three ways so every tool reads one source: Claude Code loads it via
`frontend/CLAUDE.md`, GitHub Copilot reads `.github/copilot-instructions.md`, which is a **symlink**
to it. **Edit `AGENTS.md`, never the symlink.**

Beyond that guide:

- Import generated services through the `@api` alias, never by relative path into `src/api/`.
- Shared components in `src/app/core/`, routed feature areas in `src/app/features/`, lazy-loaded via
  `loadComponent`.
- Accessibility is checked by eslint's template rules and is a requirement (NFR-7).
- The frontend never implements suitability rules
  ([ADR-010](07-decisions.md#adr-010-the-frontend-never-decides-suitability)).

### Styling

[Design language](11-design-language.md) is authoritative. Two rules the gate enforces or review
must:

- **Tokens only.** No literal colours, fonts, or spacing in a component — a hardcoded value opts
  that component out of theming.
- **Contrast holds in every theme.** `just frontend contrast` checks every foreground/surface pair
  across all four themes and runs in `just frontend check`. Adding a colour token means adding it to
  every theme and to the checker's pair list.

### Translatable strings

Mark user-visible text with `i18n="@@someId"` in templates, or `` $localize`:@@someId:text` `` in
TypeScript. Give every message an explicit id — generated hashes change when the source text is
edited, silently orphaning its translations.

```bash
just frontend extract-i18n
```

```bash
just frontend i18n
```

The check scans sources rather than the extracted `messages.xlf`, so a string added without
re-running extraction is still caught, and it fails on messages that are translated but no longer
used. An untranslated string is not a crash — `$localize` falls back to English — which is precisely
why it needs a gate: it fails silently, in a language the author does not read.

It also rejects `ß` in `de_CH`. Swiss German does not use it, and it is the single easiest thing to
get wrong when writing German from habit.

### Mobile first, literally

The phone is the design target (NFR-11), not an afterthought:

- **Author at the narrow viewport.** Base styles are the phone; media queries only ever add width.
  A component that needs a media query before it works is a bug.
- **Check at 360 px** before considering a component done. Not after review.
- Primary actions within thumb reach; touch targets at least 44 px.
- Cooking mode has its own rules — one step per screen, wake lock, glanceable at a metre. See
  [Architecture](04-architecture.md#cooking-mode-is-a-distinct-presentation).

## Contributing

1. **Branch.** Do not commit to the default branch.
2. **Small changes.** One volatility per change where possible.
3. **Update the documents.** A change that alters a decision updates
   [Decisions](07-decisions.md); a change that introduces a new volatility updates
   [Volatility analysis](03-volatility-analysis.md). Documentation drift is a defect.
4. **`just check` passes.** No exceptions. Run it per unit, not once at the end. If the change
   touches the frontend, **`just e2e` passes too**, and you have looked at the screenshots it
   produced.
5. **Tests were written first.** A pull request whose tests were clearly written after the code is
   an acceptable outcome only when adding tests to pre-existing code; say so.
6. **`just openapi` has been run** if the API changed, and the regenerated `openapi.json` is in the
   commit.
7. **Explain the why.** The commit message should say what changed and why, not restate the diff.

### Adding a feature — the procedure

Do not start by asking which service owns it. Ask:

1. What varies here, and why?
2. Is it covered by an existing volatility? If so, extend that service rather than adding one.
3. If genuinely new, does it vary over time *and* across installations? If neither, do not
   encapsulate it.
4. Which layer: a sequence (Manager), a stateless activity (Engine), access to something external
   (Resource Access), or cross-cutting (Utility)?

A feature that cannot be placed this way is usually one that is not yet understood. Say so in the
pull request rather than forcing it into the nearest service.

## Testing against a real model

`ModelAccess` has two test files. The ordinary one stubs the transport, which is what makes the
cases that matter — refused, unreachable, an answer that is not the shape it was asked for —
testable at all; a live endpoint will not produce those on demand.

The other is marked `live` and is excluded from `just check`, because a suite that needs a running
model is a suite nobody runs. It exists to check the assumption underneath the stubs: that the
provider really does speak the wire format we write. Run it when changing anything about how a
provider is reached:

```bash
QUOOKLY_INFERENCE_BASE_URL=http://localhost:8000/v1 \
QUOOKLY_INFERENCE_MODEL=your-model \
just backend test -- -m live
```

Any OpenAI-compatible server works ([ADR-026](07-decisions.md#adr-026-one-openai-shaped-wire-format-not-a-provider-plugin-system)):
vLLM, Ollama, llama.cpp, LM Studio locally, or a hosted provider with `QUOOKLY_INFERENCE_API_KEY`.

## The captured page corpus

`backend/tests/fixtures/pages/` holds schema.org metadata blocks exactly as four publishers served
them. This is the mitigation the roadmap names for interpretation risk: a change to the reader is
measured against what sites actually publish rather than against what is convenient to invent.

Only the metadata is kept, not the page markup — the blocks are the part being read, and megabytes
of HTML would be keeping the wrong thing. Refresh with:

```bash
cd backend && uv run python tests/fixtures/capture.py
```

The suite never fetches. A test failing *after* a refresh is real news about how a site has changed
its shape, and worth reading as such rather than fixing by adjusting the assertion.

## Reference data

`reference/` holds the published documents the shipped nutrition seed is derived from — today the
Swiss Food Composition Database as an `.xlsx`. They are in the repository rather than downloaded on
demand for two reasons.

They are the **provenance** of every figure a cook sees. `backend/seed/nutrition.swiss.json` is
derived; this is what it was derived from, and a number on a screen should be traceable to a
published row in a document somebody can open.

And **the links do not survive**. The Swiss workbook is published at a path containing the month it
was released, so a build step that fetched it would work until the next edition came out and then
quietly stop.

Each builder checks the document's SHA-256 before reading it, because the mappings pick rows by
number: a different edition can renumber, rename or withdraw one, and the failure would be silent —
plausible figures against the wrong food. Refreshing a dataset therefore means replacing the file,
updating the digest in the builder *and* in `reference/README.md`, re-running the builder, and
reading the diff. A publisher revising a figure is news worth looking at.

    cd backend && uv run --with openpyxl python seed/swiss.py

`openpyxl` is not a project dependency: the builders run by hand when a publisher releases an
edition, and the application never reads a spreadsheet.
